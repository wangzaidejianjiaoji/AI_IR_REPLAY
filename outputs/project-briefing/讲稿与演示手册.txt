逐页讲稿

第1页 AI 代码审查项目
核心信息：实现、使用与验收
讲稿：今天讲完整的 AI 代码审查项目，包括平台接入、知识理解、专业角色、工程校验、报告和验收。GVS 与 infer 用作业务背景，不展开算法实现。当前依据本地实现，价值和质量指标仍需试点验证。
依据：go.mod，GO_AI_PR_Review.md

第2页 项目解决的协作问题
核心信息：把变更风险转化为可核验的问题线索
讲稿：这是项目目标，不是已证实的效率提升。审查发生在变更层面，帮助团队共同讨论问题。人工审查、编译和测试仍需要保留。先讲使用价值，再讲实现和限制。
依据：internal/agent/agent.go，internal/notifier/notifier.go

第3页 当前能力与验收边界
核心信息：已有代码实现，不等于已完成线上验证
讲稿：这页明确事实和承诺边界。多角色和模型确认并不保证无漏报。全仓扫描和自动修复都没有实现，不能当作本次上线内容。
依据：cmd/agent/main.go，internal/agent/factory.go，internal/review/service.go

第4页 三个系统的关系
核心信息：审查系统读取变更，业务系统提供领域上下文
讲稿：GVS 与 infer 是被审查仓库，不会链接到审查二进制。审查服务不需要 GPU 或厂商 SDK。两端协议漂移需要领域背景，正是知识文档的用途。此处只介绍关系。
依据：go.mod，docs/gvs-code-understanding.md，docs/gvs-infer-code-understanding.md

第5页 审查入口
核心信息：共享核心流水线，去重与副作用各有区别
讲稿：轮询不是 webhook。常驻启动会立即执行一轮，忙时跳过新的触发。时间窗口在 RunOnce 检查。本地 patch 不访问 GitHub，但开启理解仍会访问 Codeup 和模型。
依据：cmd/agent/main.go，internal/review/service.go，internal/scheduler/scheduler.go

第6页 完整审查流水线
核心信息：各阶段分别解决范围、判断与输出问题
讲稿：全局理解、专业审查和确定性校验是不同层。模型负责分析语义，工程代码约束范围和协议。最终确认随理解开关装配，关闭时兼容旧流程。每一步都有失效边界。
依据：internal/review/service.go:302，internal/coordinator/coordinator.go:83

第7页 代码理解与变更意图
核心信息：来源 SHA 约束知识版本，变更分析建立共同上下文
讲稿：知识更新不是每轮必调用模型。初始化没有自动获取全仓源码，不能称为已经完成全量理解。专业角色收到 ChangeContext 摘要，未直接拿到整份知识。同步失败非 strict 时使用空上下文，旧知识兜底是待改进项。
依据：internal/understanding/manager.go:56，internal/analyzer/change.go，internal/review/service.go:345

第8页 8 个专业审查角色
核心信息：角色代表审查视角，实际参与由配置和路径决定
讲稿：8 个角色使用共享实现，区别在提示词和规则，不是 8 个独立训练模型。不存在单独的并发、资源、数据流角色。理解、分析与确认是额外调用职责，不要混淆角色数量和调用次数。
依据：internal/agent/factory.go

第9页 打包与角色分配
核心信息：按包和路径分配作业，减少重复上下文
讲稿：本地复现 src/models/yolov5_model.cpp 与 test_model 的测试文件只获得全局角色，没有算法、性能、测试角色。启用不等于参与。打包按文件数拆分，不是语义调用链完整性证明。
依据：internal/packager/packager.go，internal/coordinator/coordinator.go

第10页 工程校验能做什么
核心信息：校验提高约束强度，但不能证明问题真实
讲稿：至少一个引用出现在所有 diff 中就通过启发式，不能保证引用和问题文件对应。确认白名单只限制文件加行号，没有候选身份。不能把这一层叫零误报保障。
依据：internal/locator/locator.go，internal/reflector/reflector.go，internal/coordinator/confirmer.go

第11页 失败与降级处理
核心信息：报告必须让团队看见审查的不完整
讲稿：现有代码拦截部分失败，但部分角色失败不强制阻断。成功角色统计仍把失败角色计入，是已知问题。文件数量全覆盖不能证明文本完整，因为仍有字节预算截断。
依据：internal/review/service.go:306，internal/coordinator/coordinator.go:173

第12页 演示样例与输入证据
核心信息：本地 sample.patch，Mock 返回预设问题
讲稿：案例是 testdata/sample.patch 与本地 Mock 的预设响应。不能作为真实模型准确率数据，归一化缺陷是否成立仍取决于模型契约。这套 Mock 没有开启理解分析和确认，完整闭环要看相应单元测试或隔离的真实试点。
依据：testdata/sample.patch，tools/mockllm/main.go，configs/config.mock.yaml

第13页 演示结果的阅读方法
核心信息：先看执行状态，再看位置、证据和建议

第15页 测试的验收矩阵

第16页 状态与 dry-run 边界

现场演示步骤（约8分钟）
1.在项目根目录打开两个终端。使用Go1.23或工作区已有go.exe。
2.终端一执行：go run ./tools/mockllm
3.看到监听127.0.0.1:19090后，终端二执行：
go run ./cmd/agent -config configs/config.mock.yaml -diff testdata/sample.patch -dry-run
4.先标注Mock预设响应，再解释文件/角色、风险顺序、失败与过滤。
5.对照sample.patch与Mock源代码，展示不存在的weights/model_config.json被定位过滤。
6.说明此Mock未开启知识/分析/确认，不能代表真实模型效果。
7.展示本轮已生成的Mock演示报告.txt作为离线备份。模型和Codeup均未参与此演示。
8.关闭终端一的服务（Ctrl+C）。

演示故障备份
端口19090占用：不要结束不明进程，直接用报告文本讲解。
工具链未配置：可使用 .gotmp/go1.23.12/go/bin/go.exe 替代 go。
编译失败或现场网络不可用：用报告与PPT离线讲解，本地Mock不需要外网。
涉及真实仓库：必须先准备独立基线与知识副本，默认不在现场切换到config-codeup.yaml。

团队FAQ

1. 研发：报告零问题能直接合并吗？
不能。检查失败、过滤、截断和专项角色覆盖，再运行测试与人工评审。

2. 研发：报告里的行号是什么？
新文件 diff hunk 的定位，可容错吸附或降级文件级。发布 API 当前是全局评论，不是逐行 inline。

3. 研发：规则和模型谁决定问题？
规则补充检查视角，模型分析候选，工程代码约束位置和格式。开启理解时有最后模型确认，仍需人工复核。

4. 研发：如何驳回误报？
记录源码 SHA、实际控制流、触发条件与反例。当前没有自动反馈学习，先由团队人工维护规则/提示词。

5. 测试：Mock 能验证什么？
现有 Mock 配置只验证专业角色与工程流水线，未开启理解/最终确认；返回预设数据不能证明真实准确率。

6. 测试：如何计算准确率和漏报？
逐项人工核验的报告问题作为 Precision 分母；Recall 只在完整标注的已知缺陷集合上计算。

7. 测试：文件覆盖显示100%可信吗？
文件数纳入不代表全文输入。需要另外核对预算截断、路径过滤与角色分配。

8. 测试：本轮发现了哪些可复现问题？
state.Set 写失败仍推进内存 SHA；infer 的 C++ 模型/测试文件缺少算法、性能、测试专项分配。复现记录见项目说明。

9. 负责人：可以直接多实例部署吗？
本地 mutex 不提供跨进程互斥，状态与知识共享写入、评论去重都有竞态。先单实例，再设计分布式控制。

10. 负责人：费用可以固定估算吗？
按实际模型输入输出、包×分配角色、分析/确认/知识更新以及重试统计，再核对供应商计费。当前没有实测固定费用结论。

11. 负责人：哪些数据会进入外部服务？
模型请求可包含 diff、规则、变更上下文和全局知识。代码还可能进入报告/日志。上线前确认允许的仓库和供应商政策。

12. 负责人：下一阶段怎么批准？
明确试点仓库、人工核验负责人、预算上限和接受门槛。先处理 P1，再 dry-run 收集真实质量与人工成本。

13. 全员：dry-run 会改变本地数据吗？
会。Codeup 成功审查仍可推进基线，理解更新仍可写文档，外部模型仍可能收费。应独立 state_path 和文档副本。

14. 全员：为什么两份理解文档保留旧 SHA？
SHA 标记源码快照。文档维护不是源码升级，本轮没有远端最新 HEAD 核验，不能手改 SHA 宣称最新。

15. 全员：能否宣称专利创新或优于竞品？
目前没有外部版本核验、受控实验或专利检索依据。本轮材料不作这种结论。
