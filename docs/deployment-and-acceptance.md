# AI 审查部署、运行与验收

维护日期：2026-10-15。依据当前工作区；最终全量 Go 测试与 vet 通过，不能据本文认定已上线。真实模型、GitHub/Codeup 写入、Docker 和原生 Linux 运行未作为本次验收。参见 [项目说明](../GO_AI_PR_Review.md)、[大变更与续审](large-review.md)、[自审记录](review-self-audit.md)、[需求记录](../prd.md)。

## 配置与持久化

| 项目 | 当前要求 |
|---|---|
| Go | 模块声明 Go 1.23；本机使用已安装工具链，业务仓库版本另行管理 |
| 模型 | 仅 Kimi → MiniMax；主备 endpoint、key、模型名和超时有效；开启金额预算时两者价格均须配置 |
| 运行目录 | `review.runtime_dir` 默认 `./data/review-runtime`；`AGENT_REVIEW_RUNTIME_DIR` 覆盖。参与串行调度的实例必须指向同机同一目录 |
| 响应与知识缓存 | `review.checkpoint_dir` 默认 `./data/checkpoints`；显式 `-checkpoint-dir ""` 关闭响应缓存。目录可含业务代码响应，按业务数据控制访问并持久化 |
| 状态与知识 | 每仓库独立 `codeup.state_path`、`understanding.document_path`；试点与正式路径隔离，明确首次基线策略 |
| 知识来源 | 版本文档必须有匹配的 `SOURCE-REPOSITORY`、有效且一致的 `SOURCE-SHA`；缺失或冲突不能因 SHA 等于 HEAD 而复用。首次初始化需 `snapshot_repository` 的固定提交对象 |
| 发布 | 核对 `dry_run`、`notification.pr_comment`、`codeup.commit_comment/mr_comment`；dry-run 仅阻止评论，仍可能收费、写知识和推进基线 |
| 预算 | 调用、预留 Token、时长和可选金额限制按每个 PR 实际尝试装配；失败请求及主备重试也消耗预算 |
| 管理接口 | 默认回环；触发需管理令牌；非回环监听需额外控制访问，服务自身无 TLS |

程序不自动读取 `.env`；凭据通过环境变量或外部运行脚本注入。示例配置中的凭据使用环境占位符，禁止粘贴展开后的配置或环境值。配置校验不能证明远端 key、模型和仓库权限可用。已加载配置中模型服务返回的错误会做凭据脱敏。

同一运行目录中的 `execution.lock` 限制一个实际审核流水线，`tasks` 清单保存待执行/中断任务，`models` 保存供应商冷却，`published` 保存发布回执。冷却通过 `WithQuotaDirectory` 与响应目录分离，关闭响应缓存也不会关闭供应商冷却。原有状态/知识实例锁仍保留；单机锁不提供跨主机协调。

## 升级与启动

本轮未停止用户真实审核进程，未覆盖其运行二进制。上线步骤必须由操作方执行：

1. 保存配置标识、源码版本与未提交差异，备份状态、知识及运行目录；不记录凭据值。
2. 停止全部旧审核实例及守护进程，核对退出。旧程序不遵守新增共享运行锁，不能与新程序混跑；不要删锁文件代替停止进程。
3. 构建当前源码新二进制，再启动。原有 `start-persistent.ps1`、`start-persistent.sh` 和指定 MR 参数保持兼容，详见 [启停说明](persistent-control.md)。脚本不会自动证明已有二进制等于当前源码。
4. 所有参与实例使用同一绝对运行目录；响应目录可按实例隔离。检查目录权限、磁盘空间和状态/知识来源。
5. 先用隔离状态和知识的 dry-run 试点，检查日志中的目标版本、缓存命中、失败阶段、覆盖与基线，再核验真实发布权限。

Windows 本机构建示例（先完成停机步骤）：

```powershell
go build -o bin/gvs-pr-agent.exe ./cmd/agent
.\start-persistent.ps1
```

Linux 启动需要 Bash、flock，后台模式另需 nohup；已有可执行文件不会自动重新构建。本次只有 Linux 交叉编译及 Git Bash 路径验证，没有原生 Linux 生命周期验收。容器使用持久化 data/docs 和只读 configs；首次知识初始化还需挂载业务 Git 对象并填写容器可见 `snapshot_repository`。不同容器要共享同一宿主运行目录且锁语义有效，不能只靠目录名称相同。

## 扫描、版本与续审

每轮扫描最多运行一个实际审核流水线。队列按上次尝试最早优先，结合重试时间和存活所有者轮询恢复；失败或冷却不会被记为成功。每个 PR 重新建立 Kimi 优先会话，本次尝试降级到 MiniMax 后不回跳；共享供应商冷却跨进程保留，全部冷却时避免新请求，但已有成功响应可以复用。

各入口启用阶段响应缓存与固定知识快照；相同版本、规则、配置及请求才能复用。缓存接受前仍经过相应协议校验，响应/知识落盘失败会阻断完成。缓存不是平台成功基线，删除缓存不会使已完成版本自动重审。没有自动过期清理，需自行管理容量。

Codeup MR 身份覆盖源/目标 SHA、元数据和配置依赖，目标分支单独变化也会重新审查；旧尝试完成不能把新版本清单标为成功。GitHub diff 使用固定 SHA compare，发布前复查 SHA、开启状态及元数据。复查与发布存在时间窗口，不能承诺原子快照发布。

发布成功后保存本地回执，随后基线失败时可据回执减少重复评论。远端成功到回执写入之间仍有故障窗口；回执损坏或落盘失败应先核对平台评论再处理，不能盲目删除记录重跑。dry-run 和正式环境应隔离状态，不能期待移除 dry-run 后同版本自动补发。

## 验收与故障处理

| 场景 | 验收/处理要求 |
|---|---|
| 模型限额、网络或鉴权失败 | 区分配额与普通鉴权；检查共享冷却和 PR 路由；修正凭据而非提高预算掩盖错误 |
| 包或确认超限 | 完整 hunk 可拆包；单个 hunk/候选证据超预算仍失败；不把失败的零问题报告当作通过 |
| 队列中断或版本推进 | 保留新版本清单，按重试与公平顺序恢复，旧完成记录不能覆盖它 |
| 知识来源错误 | 拒绝缺失/其他仓库/冲突 SHA，不复用错误来源作为降级快照；从可信源码重新建立 |
| 状态/响应/知识落盘失败 | 不宣告成功；恢复权限或空间后重试，保留可复用阶段结果 |
| 评论成功后本地失败 | 先核对平台和回执；远端与本地不存在事务保障 |
| 锁占用 | 检查真实进程及路径，不直接删锁；多主机需另行调度 |

本地验证命令：`go test ./...`；适用平台命令应另记退出码。Windows 原生测试、Linux 交叉编译和 Git Bash 脚本路线分别提供证据，不能替代原生 Linux 或 race。当前环境缺少 race 所需 cgo 工具链，不宣称 race 通过。最终工作区 `go test -count=1 ./...`、`go vet ./...` 均退出 0；PowerShell 与 Git Bash 脚本兼容测试通过。

每次试点记录源码提交与未提交状态、配置标识、仓库/源/目标/知识 SHA、模式和开关、命令退出码、覆盖与未确认数、实际 Usage/估算预算、人工核验和报告位置。真实供应商契约、费用及缺陷检出率需要单独验收。`build.ps1/build.sh` 会执行 `go mod tidy`，只读验证时不要无意修改模块文件。
