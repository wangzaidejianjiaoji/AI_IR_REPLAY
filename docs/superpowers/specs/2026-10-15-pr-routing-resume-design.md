# PR 串行调度、两级模型与断点续审设计

日期：2026-10-15。状态：用户已批准实施；以实现及最终 prd.md 的验证状态为准。

代码基线：4c9123e3。用户明确只保留 Kimi → MiniMax；GVS、infer 和后续新增实例共用一个 PR 审核执行槽。本文不包含凭据，最终的 `prd.md` 在实现、验证和自审修复后生成。

## 1. 已核实的现状

- `internal/llm/client.go` 只有主模型与一个备用客户端，现有业务配置是 Kimi → MiniMax。
- `internal/review/tasks.go` 的执行槽属于单个 Service，不能阻止 GVS 与 infer 两个进程同时审核；RunOnce 可遍历多个仓库、分支和 MR。
- `internal/llm/checkpoint.go` 已保存请求响应与供应商冷却信息，但目前只由 Codeup MR 流程在配置目录非空时装配。业务常驻配置尚未统一开启，GitHub PR 不具备同等续审保障。
- 全局分析已分批归并，专业审核已按文件数和字节预算拆包，确认已按候选数和编码后字节分批；超大单文件仍直接报错，确认给每个候选重复附完整文件 diff。
- 当前 MR 成功基线只比较源 SHA，目标 SHA 单独变化可能被跳过；并发专业结果在相同排序键下可能影响确认批次稳定性。这两项在实施阶段用回归测试验证再修复。

## 2. 选择与边界

采用共享文件调度状态、操作系统锁和现有 Go 流水线。相比新增独立调度服务，不增加服务部署和依赖；相比只改进程内互斥，可以约束现有两个常驻实例。

保障范围是同一台机器、同一共享调度目录。所有实例使用一致的可配置绝对路径；同项目默认共用 data 下的目录，其他工作目录的实例须显式指向同一个目录。不同主机不承诺全局互斥，本次不实现分布式锁。

保持原脚本名称、默认启动入口以及指定 Codeup MR 的参数。当前用户所称 PR 同时涵盖 GitHub PR 与 Codeup MR；不将现有 MR 参数冒充 GitHub 单 PR 入口。

## 3. 模型优先级

配置固定顺序：Kimi → MiniMax，沿用现有主模型与 fallback 字段，不增加其他模型接口，也不接入当前聊天会话。

保留旧主备配置的兼容映射，拒绝重复/无效启用项。密钥通过环境变量展开，不把 env.md 中的值复制进配置、文档或测试。

每个 PR 获取执行槽后建立独立路由上下文：

1. 按优先级读取供应商的持久化冷却状态，跳过尚在冷却或未启用的项。
2. 第一个未完成阶段的真实模型请求负责验证可用性，不额外发送收费探测。
3. 明确额度/速率限额立即记录冷却并切到下一项；没有已知冷却时，下一 PR 仍从最高优先级尝试。
4. 当前 PR 降级后不在中途反复向高优先级探测；已发出的并发请求仍可能完成或计费，不能保证瞬间取消供应商侧处理。
5. 网络错误和 5xx 按有限重试处理，耗尽后可进入下一可用供应商；401、普通 403、配置错误、业务输出校验错误单独披露，不能伪装为“额度耗尽”。格式错误沿用受限重试与缓存失效规则。
6. 全部模型不可用时保存中断状态及可知的下次复查时间，不发布成功报告、不推进已审基线。中断后退出本轮，不在同轮继续消耗其他 PR 的模型额度。

各级请求与重试共用本 PR 的调用、估算 Token、时长和可选费用预算。费用预算启用时，所有启用模型都必须有价格；冷却截止和费用估算都不等于供应商保证或真实账单。

## 4. 全局单 PR 调度

使用两种职责分开的共享锁：短期队列写锁维护持久化任务状态；执行锁从选中 PR 开始一直持有到完成或中断。查询列表和更新发现记录不调用模型。

- 同一共享目录的 GVS、infer、手动 MR 和后续实例必须在模型调用前竞争同一个执行锁。
- 每次扫描最多领取一个实际审核任务。已审、过滤、冲突、WIP 等跳过项不消耗本轮审核名额。
- PR 内的专业角色仍可按配置受限并发；“一次一个 PR”不等于“PR 内只能发一个请求”。
- 保留现有分支入口，但纳入同一执行槽与本轮任务额度，不能从分支路径绕开串行约束；先发现 PR/MR，再处理其余分支任务。
- 正在冷却的中断任务不持续霸占锁。可执行任务按最久未尝试、最早发现排序，使持续失败的任务不能饿死从未执行的任务。
- 手动指定 MR 仍精确选择；执行槽被占用时清晰返回忙碌，不绕过全局锁，也不悄悄改为其他任务。
- 进程崩溃由操作系统释放执行锁；持久化状态用于识别未完成任务并恢复，不能把遗留 reviewing 状态永久视作正在运行。
- 先获取执行资格，再建立本 PR 的执行预算与超时，避免把扫描等待消耗当作模型审核时间。

## 5. 续审身份与持久化

任务身份包含平台、仓库、PR/MR 编号、源/目标 SHA、差异摘要与相关配置/规则版本。GitHub 的源、目标与 diff 必须核对为同一快照；发布前再次检查版本。MR 成功基线也必须区分目标变化，旧状态须安全兼容。

保存可恢复的任务清单，覆盖知识快照、全局分批分析、摘要归并、专业包×角色、候选归并、确认批次与报告生成。稳定排序和稳定批次标识避免并发完成顺序改变恢复请求。

- 成功且通过消费者校验的结果才可复用；无效 JSON、协议遗漏、损坏缓存等不能标记阶段完成。
- 重跑复用未变的有效工作，只请求未完成或已失效的阶段。切换供应商不应迫使已经完成的其他阶段重跑。
- 记录结果实际产生的供应商、模型和原始 Usage，以及本轮缓存命中与新增请求；不得把复用当作本轮新消耗。
- 恢复时复用原任务固定的知识快照。源码、规则、相关配置或知识依赖发生不兼容变化时使相应阶段失效，不能拼接不同版本的结论。
- 更新清单和阶段结果采用临时文件替换。续审存储不可写时不能声称具有持久恢复保障，应明确失败或降级状态。
- 全部必需阶段完成后才进入发布；评论与本地落盘不构成平台事务，保留可识别版本标记并在重试前核对已有评论，降低重复发布概率，不承诺恰好一次。

## 6. 大变更优化

延续预算保护，优化材料组织而非仅提高调用上限：

1. 总 diff 按模块和大小构造稳定批次，全局分析及归并均可单独恢复。
2. 超大单文件优先按完整 hunk 拆分，保留文件头、原始行号及覆盖映射；若单个 hunk 仍超预算，明确阻断，不把缺失证据标作完整审核。本次不实现任意行裁切或 AST 级代码索引。
3. 专业作业分别保存结果；模型限额时停止派发未开始的工作，已经完成的结果继续落盘。
4. 确认批次中相同文件/证据片段只发送一次，候选通过证据 ID 引用。按实际序列化后正文大小及候选数拆批，完整验证每个候选的身份与位置。
5. 使用确定性候选排序与批次构造。任一必需阶段失败、覆盖缺口或确认遗漏阻断成功发布。
6. 测量大变更的请求数、重复证据字节、峰值输入规模和中断恢复时新增请求数；不预设 Token 节省比例或准确率提升。

## 7. 自审与修复范围

实现后检查全项目配置、平台快照、调度/状态、模型路由/预算、理解/确认、发布及启停代码。对发现的问题先构造复现或回归测试，再做最小修复；没有证据的猜测列作限制，不进行无关重构。

重点检查：所有入口是否绕过全局锁、取消后是否继续派发、目标 SHA 变化是否仍被去重、缓存是否污染版本、角色输出是否稳定、价格与用量是否正确归属、错误日志是否回显凭据、知识来源标记是否完整、发布后落盘失败如何恢复，以及启停是否影响非目标进程。

保留当前正在运行的真实实例和用户其他工作区内容。测试使用本地模拟平台/模型和临时路径；部署到正在运行的实例需单独明确实施步骤，不将测试完成等同于已上线。

## 8. 验收及交付

必需验收：

- 模拟 Kimi/MiniMax 两家端点验证调用顺序、共享冷却、下一 PR 重新按优先级选择、全部不可用退出，以及网络/认证错误分类。
- 两个及三个独立进程共享调度目录时，实际审核区间不重叠；崩溃后可接续；手动入口同样受限；每轮最多一个任务。
- 中途限额或进程退出后，以新进程恢复，相同版本已完成阶段不新增模型调用；依赖变化或损坏缓存不会错误复用。
- 大文件多 hunk、大量文件/候选、同文件多候选、编码后超预算、单 hunk 超限及确认遗漏均有覆盖测试；输入覆盖无静默裁切。
- 固定版本复查、dry-run、旧脚本名及原 MR 参数的回归测试通过。
- 全量 Go 测试、适用的并发检查、Windows 脚本回归和 Linux 交叉编译；Linux 原生测试未执行时明确标注，不冒充通过。

最终交付：实现代码、回归测试、自审问题及修复记录、更新的运行说明，以及根目录 `prd.md`。PRD 按摘要、责任与参与者、背景、目标、用户群、价值、方案与验收、发布八部分记录实际已实现/已验证/待验收状态，不编造市场规模、模型可用额度或效果指标。
